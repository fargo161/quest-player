# Deploying Quest Player

This project targets Render with PostgreSQL and external Cloudflare R2 media. Deployment requires operator-owned infrastructure and SMTP credentials. The files are configuration templates; their presence is not proof of a production deployment or festival readiness.

## Local setup

Use Node 24 and PostgreSQL 18. `docker compose up -d` starts PostgreSQL and Mailpit (local mail capture). Copy `.env.example` to `.env`, replace both secrets, then run `npm ci`, `npm run migrate`, and `npm start`. Open http://localhost:3000. Mailpit displays verification/recovery messages at http://localhost:8025. Captured mail proves the flow locally, not real inbox delivery. Compose contains intentionally local credentials and binds exposed services to loopback.

Without Docker, start your own PostgreSQL server, set DATABASE_URL, and use a local SMTP capture service or a real SMTP provider. The application requires migrations before startup. PORT is supplied by Render in production.

## Render deployment

1. Put this project in your own repository and use `render.yaml` to create the service and PostgreSQL database. Review current service pricing before provisioning. The web service uses Docker, runs as the node user, and installs from package-lock.json with npm ci.
2. Set PUBLIC_BASE_URL to the final HTTPS origin. Configure DNS and TLS for a hostname you intend to keep. Set a long random MISSION_CONTROL_PASSPHRASE. SESSION_SECRET is generated by the blueprint. Keep secrets in Render environment settings, not Git.
3. Configure SMTP_HOST, SMTP_PORT, SMTP_SECURE, SMTP_USER, SMTP_PASS and MAIL_FROM from a real mail provider. Port 587 uses SMTP_SECURE=false with STARTTLS; 465 uses true. Authenticate the sending domain with your provider. Test verification and recovery with an actual inbox and a second browser. Local Mailpit is not a production provider.
4. Render runs `npm run migrate` as the pre-deploy command. The process listens on PORT; `/healthz` checks database availability. Failed migrations or health checks must prevent release promotion.
5. Configure the quest intro_video_url in PostgreSQL to a public HTTPS media URL. R2_PUBLIC_BASE_URL is reserved configuration and does not upload media or automatically rewrite quest rows. No R2 credentials are needed to play a public video. Use a stable custom media domain where appropriate; verify content type, browser playback and an unavailable-video fallback. Text and Continue must still work.
6. Complete the operations checklist, including an actual backup/restore verification, before using the service with attendees.

Changing SESSION_SECRET invalidates signed cookies. Treat that as a deliberate account access event. Never delete or recreate the database as a normal redeploy. Take a backup before migrations. Rolling back app code does not reverse database migrations: assess schema compatibility first.

## Printed QR codes

With PUBLIC_BASE_URL set to the final origin, run:

```text
npm run qr -- --confirm-host YOUR_FINAL_HOSTNAME --output work/print-qr
```

The script writes PNG, SVG and URL text for `/start/as-above-so-below`. It rejects HTTP, localhost, temporary tunnels, obvious preview names, credentials and URL paths. The exact hostname confirmation is intentional. This validation cannot prove domain ownership or long-term availability. Scan a printed proof using an independent phone over mobile data before printing signs. The QR is an entry URL, never player identity or a login token.

## Backup and restore drill

Install PostgreSQL client utilities compatible with the server (pg_dump, pg_restore, createdb); set PG_BIN to their directory if absent from PATH. With DATABASE_URL set, run:

```text
npm run backup:verify -- --output work/private-backups
```

The database role must be able to create a fresh verification database. Use an appropriately authorized maintenance role for this drill if the runtime role lacks that right. The script keeps a consistent source snapshot, creates a custom-format dump, restores into a new random database on the same server, and compares all public tables by row count and whole-row fingerprints, including both audit histories. It never drops an existing database. It retains the dump, JSON report and verification database for inspection. A successful exit and `verified: true` are the evidence; running a command that fails is not a successful drill.

The dump and restored database contain personal data and authentication records. Restrict filesystem/database access, encrypt retained backups, and explicitly remove the disposable verification database after inspection. Do not connect the live app to it. On Windows, arrange appropriate folder ACLs; POSIX mode flags do not enforce Windows ACLs. Keep backup retention and ownership documented outside the application. The drill checks data restoration; a separate isolated app smoke test against the restored database checks usability. This script is not a managed backup schedule.

If the hosted role cannot create databases, an operator must provide an isolated restore environment and perform an equivalent documented drill with matching table/audit verification. Do not label the deployment festival-ready until this succeeds against representative data.


## Configuration references

Render service/database fields and plan identifiers follow the [Render Blueprint specification](https://render.com/docs/blueprint-spec). Confirm availability and pricing when provisioning. The PostgreSQL 18 Compose volume mounts `/var/lib/postgresql`, following the [official Docker PostgreSQL persistence guidance](https://docs.docker.com/guides/postgresql/immediate-setup-and-data-persistence/). A major-version update is not performed by simply attaching old database files to a newer server.

On Windows, compatible portable client binaries are available through the [EDB binary archive page](https://www.enterprisedb.com/download-postgresql-binaries?lang=en), which is linked from the [PostgreSQL Windows download page](https://www.postgresql.org/download/windows/). The local development restore drill used PostgreSQL 18.6 client utilities against PostgreSQL 18.4. No PostgreSQL system installation was needed.
